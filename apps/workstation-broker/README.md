# Paul OS Workstation Broker

Status: proposal-ready local prototype. Production workstation dispatch is deliberately disabled.

This solution is the thin Windows boundary for Paul OS. It contains transport, current-user proof, device-certificate proof, an ACL-restricted named-pipe handshake, and a local Plugin execution interface. It contains no workflow decisions, model access, database access, Plugin credentials, or authority-policy logic.

## What runs today

- `PaulOs.WorkstationBroker.Service` is a .NET 10 worker that can run as a Windows Service. Development fixture mode consumes one synthetic signed order through the real worker/session path. Its production transport and local Plugin executor fail closed until enterprise activation supplies reviewed implementations.
- `PaulOs.WorkstationBroker.Companion` contains a current-user WAM adapter and the named-pipe client. Development fixture mode creates a bounded synthetic identity token and sends user presence through the exact current-user pipe. It does not request a production token without explicit configuration and an assigned work order.
- `PaulOs.WorkstationBroker.Core` verifies signed work orders, exact actor/device/lease/nonce bindings, freshness, and replay protection.
- `PaulOs.WorkstationBroker.Tests` launches the compiled Service and Companion as separate processes for resume and replay scenarios. It also exercises expiry without a companion, current Windows certificate APIs, and a real named pipe whose DACL contains only the current user and LocalSystem.
- `PaulOs.ControlPlane.Client` is generated by Kiota from `/live`, `/ready`, and `/v1/session` in the repository OpenAPI document. Work-order endpoints are intentionally deferred until the central ledger contract is implemented.
- The WiX project produces an unsigned, per-machine proposal MSI. The installed service starts in disabled mode and cannot execute local work.

The Windows Service hosting pattern follows the [.NET 10 Windows Service guidance](https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service). The current-user seam follows the [MSAL.NET WAM guidance](https://learn.microsoft.com/en-us/entra/msal/dotnet/acquiring-tokens/desktop-mobile/wam). Named-pipe authorization uses the [.NET `PipeSecurity` API](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.pipesecurity?view=net-10.0). Client generation follows the [Microsoft Kiota documentation](https://learn.microsoft.com/en-us/openapi/kiota/).

## Security invariants

1. A workstation work order is valid only for one immutable release digest, entry resource, exact Plugin version/digest/tool, actor, Windows SID, device-certificate thumbprint, nonce, lease, and freshness window.
2. User-only and device-only execution are both forbidden. The companion supplies current-user proof; the service signs the exact work-order nonce with the configured machine certificate. Both are verified before the run can become leased.
3. Any workstation dependency holds the whole run in `waiting_for_user`. There is no silent control-plane fallback.
4. Waiting runs permit no external effects. They expire without late work and emit one deterministic digest-item key.
5. Central-only runs remain immediately eligible for control-plane execution.
6. The named pipe grants access to only the exact user SID and LocalSystem. The signed payload and application-level handshake remain mandatory even after ACL admission.
7. Access tokens and device signatures are never logged. Persisted evidence contains only SHA-256 digests.
8. Fixture identity and ephemeral development certificates are rejected outside Development mode.

## Build and test

Install the pinned .NET SDK in `global.json`, then run from the repository root:

```powershell
dotnet restore apps/workstation-broker/PaulOs.WorkstationBroker.slnx --configfile apps/workstation-broker/NuGet.Config
dotnet build apps/workstation-broker/PaulOs.WorkstationBroker.slnx -c Release --no-restore
dotnet test apps/workstation-broker/tests/PaulOs.WorkstationBroker.Tests/PaulOs.WorkstationBroker.Tests.csproj -c Release --no-build --no-restore
apps/workstation-broker/scripts/generate-client.ps1
apps/workstation-broker/scripts/build-proposal-msi.ps1
apps/workstation-broker/scripts/run-fixture-demo.ps1 -Scenario resume -SkipBuild
```

The fixture runner also accepts `replay` and `expiry`. Fixture mode is hard-bound to the Development environment. Its integrity key is public test material, not an authentication secret, so it demonstrates protocol shape rather than real user identity.

The client generator is pinned by `.config/dotnet-tools.json`; generated code and `kiota-lock.json` are committed. The runtime package remains pinned to the compatible `Microsoft.Kiota.Bundle` 1.22.2 dependency family.

WiX 7 was not adopted because its local build requires accepting an additional maintenance-fee EULA. The proposal artifact uses the pinned open-source WiX 4.0.6 SDK instead. The MSI is unsigned and must not be distributed as a production package.

## Honest limits

- There is no live enterprise identity tenant, managed device certificate, approved gateway, production control-plane work-order endpoint, durable server replay ledger, code-signing certificate, or managed deployment in this repository.
- Replay protection in the executable prototype is process-local. Production requires an append-only, transactional server record keyed by work-order nonce and invocation key.
- The production service transport and local Plugin executor are refusal implementations. They cannot perform real workstation work.
- The WAM adapter is present and compile-tested, but no credentialed token acquisition runs in CI.
- The two-process fixture uses a synthetic no-effect `fixture.echo` tool. It cannot read files, start arbitrary programs, use Plugin credentials, or produce external effects.
- The MSI is built and structurally testable locally, but it is not a certified or signed enterprise release.

These are Enterprise Activation prerequisites, not hidden fallbacks.
